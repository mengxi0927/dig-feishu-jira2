# Jira 派工日志与月度补录

2026-09-21：已实现 monthly-delta 策略。生产部署和历史基线确认是启用前的独立步骤；本地开发不改变正在运行的定时任务。

## 业务规则

- 每天北京时间06:00，date为昨天，回溯最近30天。为完整刷新未结算期间，必要时扩展到该期间首日。发现旧来源消失时扩大到本年范围核查，避免把滑出窗口当作删除。
- 期间为上月22日至本月21日。22日先刷新截至21日的正常工时，再关闭该期间；漏跑时下一次执行自动补做月度核对。
- 月度读取当年1月1日至截止日。刚结束的未结算期间走正常写入，更早关闭期间才生成补录。上年度已结算数据不做跨年追溯。
- Jira同步表格-派工追加新增/修改/删除日志，不覆盖、删除旧日志。日志只能反映同步观察到的变化，不能还原两次查询之间的全部操作。
- 工时信息保持原来的“日期＋项目号＋姓名”合并规则、日工时来源及四位小数舍入，只新增allocationId列表。后台保存每条派工贡献，不改变汇总粒度。
- 每月建立工时信息-补录-x月。9月表作为模板并直接复用。状态按YYYY-MM保存表ID；次年表名带年份，避免重名。无差额月份也创建空月表。
- 差额写入“补录工时（小时）”：5→8为+3，8→5为-3，删除5为-5，新增5为+5。同月5→8→6最终补录+1，日志保留观察到的中间变化。
- 项目、人员、日期变化按旧归属扣除、新归属增加，分别判断期间。补录表原“工时（小时）”不写差额，金额及审批字段不由同步填写。

## 持久化与防重

allocationId是接口字段。allocationId|day、变更事件ID、同步明细键由程序生成。事件ID包含持久化版本，区分多次重复发生的5→8。

原STATE_FILE新增assignment，不替换报工状态：
- observed：最近观察到的源状态。
- accounted：已写正常工时或已生成补录的基准，不代表人工补摊已经审批。
- closedThrough：已关闭的期间截止日。
- months：月表ID、名称和字段准备状态。
- pending：远端写入前保存的完整待执行批次，失败后先恢复原批次。

月度完成前保存不可覆盖的assignment-snapshots/YYYY-MM-rN.json，含源状态、正常工时及补录明细。状态和快照必须一起备份。

日志按事件ID、补录按明细键读取远端防重，覆盖“写入成功但响应丢失”的情况。正常表按原汇总键回读恢复，只删除后台已管理且处于未结算范围的消失汇总行。

## 字段与月表

初始化自动补齐缺少的技术字段；同名字段类型不匹配时拒绝继续。
- 日志：allocationId、变更事件ID、来源唯一键（文本），工时日期（日期），变更前工时、变更后工时（数字），派工状态（新增/修改/删除单选）。
- 正常工时：保留原项目号、姓名、日期、工时字段，加allocationId（文本）。
- 月表：项目号、姓名、日期、allocationId、补录工时（小时）、同步明细键（文本）、调整期间（文本）。

新月表先创建字段ID，再改写公式中的本表和本表字段引用，外部项目/人员表引用保持原目标。当前飞书接口不能直接设置查找引用字段，新表将其表达式建立为等价公式；原模板类型不变。视图布局、自动化和权限规则不会随字段复制。

已发现：模板“派工区间”按26日切月，与同步22日规则不同。程序保留现有公式，另以“调整期间”保存处理年月。使用依赖“派工区间”的下游分摊前，需要业务方统一公式口径。“月份验证”依赖TODAY，不能作为固定结算标志。

## 首次启用

配置ASSIGNMENT_STRATEGY=monthly-delta，FEISHU_BACKFILL_TEMPLATE_TABLE_ID=tblVEzscKMM0EGwh，FEISHU_DAILY_HOURS_FIELD=工时（小时）。仍需原有凭据、日志/正常表ID和唯一主机写入配置。

1. 备份生产配置、状态和正常表，停用旧派工调度。
2. 执行 node src/cli.js preview --date YYYY-MM-DD（北京时间昨天），检查baseline.hash与逐汇总键差异。预览不写飞书。
3. 本年Jira汇总和现有正常工时必须对齐；缺失历史、手工调整、重复键不能自动视为新增。先核对差异，不覆盖历史来绕过检查。
4. 执行 node src/cli.js initialize --date YYYY-MM-DD --baseline-hash <预览摘要>。摘要须仍匹配当前数据。补齐技术字段，仅向匹配的正常行补写allocationId，不改工时，保存明细基线。
5. 再预览变更日志、正常工时与月度差额，执行sync并启用原每天06:00调度。

HTTP保留/api/preview和/api/sync；新增/api/initialize，接收date和baselineHash。所有写入使用原主机保护与文件锁，正式写入只接受昨天，历史日期仅允许预览。

未初始化时拒绝正式同步，不会把全年记录重复补录。状态丢失后不能只凭合并的allocationId列表恢复，必须重新核对基线。

ASSIGNMENT_STRATEGY=legacy只保留旧代码兼容和回滚能力。启用新策略后不能直接让旧程序写同一日志和状态，回滚应使用上线前备份。
